# GGUF Tool Calling Implementation Plan

**Project:** DeepCoderX  
**Date:** July 6, 2025  
**Priority:** Critical - Core Functionality Restoration  
**Status:** Ready for Implementation

---

## Executive Summary

This plan addresses the critical failure in GGUF model tool calling by implementing a specialized GGUF handler that uses manual prompt engineering and pattern matching, while maintaining the unified architecture achieved in the completed legacy migration.

**Core Strategy:** Create GGUF-specific components that integrate seamlessly with the existing unified architecture, Tool Registry Pattern, and standardized error handling.

---

## 1. Current State Analysis

### 1.1 What's Working ✅
- **Unified Architecture:** Successfully migrated and functional
- **Tool Registry Pattern:** All 7 OpenAPI 3.1 tools registered and working
- **MCP Client/Server:** Complete file system operations support
- **Cloud Models:** DeepSeek and OpenAI working with native tool calling
- **Error Handling:** Standardized across all components

### 1.2 What's Broken ❌
- **GGUF Tool Calling:** Local models cannot execute any file system operations
- **Local Handler Logic:** Incorrectly assumes OpenAI-style tool calling
- **Model Type Detection:** No distinction between OpenAI-compatible and GGUF models

### 1.3 Root Cause
The `LocalOpenAIHandler` assumes GGUF models can:
1. Process OpenAI tool schemas
2. Return structured `tool_calls` in responses
3. Handle automatic tool execution

**This is fundamentally incorrect for GGUF models.**

## Phase 2: Core GGUF Handler (Days 3-4)

### 3.4 Create GGUFLocalHandler

**File:** `services/gguf_handler.py`

**Purpose:** Main handler for GGUF models with manual tool calling

**Integration Points:**
- Inherits from existing `CommandHandler` base class
- Uses existing `ToolExecutor` for file operations
- Integrates with unified error handling
- Maintains conversation history

**Core Implementation:**
```python
class GGUFLocalHandler(CommandHandler):
    def __init__(self, context: CommandContext):
        super().__init__(context)
        self.prompt_builder = GGUFToolPromptBuilder()
        self.tool_parser = GGUFToolCallParser()
        self.context_manager = GGUFContextManager()
        self.tool_executor = ToolExecutor()
        self.max_iterations = 5
        
    def can_handle(self) -> bool:
        # Handle all inputs when GGUF is the active model
        return self._is_gguf_model_active()
        
    def handle(self) -> None:
        # Multi-turn conversation loop with tool calling
        iteration = 0
        
        while iteration < self.max_iterations:
            # Build prompt with embedded tools and history
            prompt = self.prompt_builder.build_prompt(
                user_input=self.ctx.user_input,
                conversation_history=self.context_manager.get_conversation_history(),
                available_tools=self._get_available_tools()
            )
            
            # Generate response from GGUF model
            response = self._generate_gguf_response(prompt)
            
            # Parse for tool calls
            tool_calls = self.tool_parser.parse_response(response)
            
            if not tool_calls:
                # No tools called, return final response
                self.ctx.response = self._extract_clean_response(response)
                break
                
            # Execute tools and prepare for next iteration
            tool_results = self._execute_tool_calls(tool_calls)
            
            # Update context with tool results
            self.context_manager.add_tool_results(tool_calls, tool_results)
            iteration += 1
            
        if iteration >= self.max_iterations:
            self.ctx.response = "Task completed after maximum tool calling iterations"
```

## 4. Detailed Implementation Specifications

## 4.1 GGUF Tool Call Protocol

### 4.1.1 Tool Call Format
**Standard Pattern:** `<tool_call>function_name(json_arguments)</tool_call>`

**Examples:**
```xml
<tool_call>write_file({"path": "test.txt", "content": "Hello World"})</tool_call>
<tool_call>read_file({"path": "config.py"})</tool_call>
<tool_call>list_dir({"path": "."})</tool_call>
<tool_call>mkdir({"path": "new_directory"})</tool_call>
<tool_call>move_file({"source": "old.txt", "destination": "new.txt"})</tool_call>
<tool_call>stat({"path": "file.txt"})</tool_call>
<tool_call>run_bash({"command": "ls -la"})</tool_call>
```

### 4.1.2 Prompt Template Structure
```
You are an AI assistant with access to file system tools. When you need to use a tool, format your response like this:

<tool_call>function_name({"parameter": "value"})</tool_call>

Available tools:
- write_file(path, content): Creates or overwrites a file
- read_file(path): Reads file content
- list_dir(path): Lists directory contents
- mkdir(path): Creates a directory
- move_file(source, destination): Moves or renames files
- stat(path): Gets file/directory information
- run_bash(command): Executes shell commands

Examples:
User: Create a file called hello.txt with content "Hello World"
Assistant: I'll create that file for you.
<tool_call>write_file({"path": "hello.txt", "content": "Hello World"})</tool_call>
File created successfully! The file hello.txt now contains "Hello World".

User: List the files in the current directory
Assistant: I'll list the current directory contents for you.
<tool_call>list_dir({"path": "."})</tool_call>

Current conversation:
{conversation_history}

User: {user_input}
Assistant: 
```

### 4.1.3 Response Processing
1. **Extract Tool Calls:** Use regex to find all `<tool_call>...</tool_call>` patterns
2. **Parse Arguments:** Extract function name and JSON arguments
3. **Execute Tools:** Call ToolExecutor with parsed arguments
4. **Format Results:** Inject tool results back into conversation
5. **Continue or Finish:** Determine if more iterations needed

## 4.2 Error Handling Strategy

### 4.2.1 Tool Call Parsing Errors
```python
class GGUFParsingError(Exception):
    """Raised when tool call parsing fails"""
    pass

def handle_parsing_error(self, error: str, raw_response: str) -> str:
    """Provide helpful feedback for parsing errors"""
    return f"I attempted to use a tool but the format was incorrect. Let me try again: {error}"
```

### 4.2.2 Tool Execution Failures
```python
def handle_execution_error(self, tool_call: Dict, error: str) -> str:
    """Handle tool execution failures gracefully"""
    return f"Tool execution failed: {error}. Let me try a different approach."
```

### 4.2.3 Context Window Management
```python
def manage_context_window(self) -> None:
    """Truncate context when approaching limits"""
    if self.context_manager.get_token_count() > self.max_context_tokens:
        self.context_manager.truncate_context(self.max_context_tokens * 0.8)
```

## 4.3 Performance Considerations

### 4.3.1 Token Optimization
- **Efficient Prompts:** Minimize token usage in tool examples
- **Context Truncation:** Keep only recent relevant conversation
- **Tool Filtering:** Only include available tools in prompts

### 4.3.2 Response Time
- **Parallel Execution:** Execute multiple tools concurrently when possible
- **Caching:** Cache frequent tool call patterns
- **Early Termination:** Stop iteration when task is complete

### 4.3.3 Memory Management
- **History Limits:** Prevent unlimited conversation growth
- **Tool Result Cleanup:** Remove old tool results from context
- **Model Unloading:** Properly manage GGUF model memory

## 5. Risk Mitigation

## 5.1 Implementation Risks

### 5.1.1 High Risk: Tool Call Format Inconsistency
**Risk:** GGUF models may not consistently follow tool call format
**Mitigation:** 
- Extensive prompt engineering with multiple examples
- Robust regex patterns with fallback parsing
- Error recovery mechanisms

### 5.1.2 Medium Risk: Performance Impact
**Risk:** Multiple model calls may be slow
**Mitigation:**
- Iteration limits (max 5 per user input)
- Efficient prompt construction
- Tool execution optimization

### 5.1.3 Low Risk: Configuration Complexity
**Risk:** Users may misconfigure model types
**Mitigation:**
- Clear documentation
- Validation in config loading
- Helpful error messages

## 5.2 Rollback Strategy

### 5.2.1 Gradual Deployment
1. **Feature Flag:** Add `GGUF_TOOL_CALLING_ENABLED` config option
2. **Parallel Testing:** Run both old and new handlers for comparison
3. **Incremental Rollout:** Enable for specific model types first

### 5.2.2 Fallback Mechanisms
```python
def handle_with_fallback(self) -> None:
    """Try GGUF handler, fall back to simple response if it fails"""
    try:
        self._handle_with_tools()
    except Exception as e:
        console.print(f"[yellow]Tool calling failed: {e}[/]")
        self._handle_without_tools()
```
